# Building rsbtd

Installing the prebuilt packages is covered in
[README.md](README.md#installing); this document is about producing the builds
yourself and hacking on the code.

## Building from source

```sh
git submodule update --init --recursive     # vendored libtorrent + its deps
cargo build --release --features vendored -p rsbtd -p rsbtctl
./target/release/rsbtd --config rsbtd/etc/rsbtd.toml
```

Build requirements: Rust via rustup (the toolchain is pinned by
`rust-toolchain.toml`), a C++20 compiler (the C shim requires it and
CMake enforces it; see `libctorrent/CMakeLists.txt`), CMake ≥ 3.25,
Boost headers,
OpenSSL, and libclang — bindgen uses it to generate the FFI bindings
(`clang-devel` on Fedora/RHEL, `libclang-dev` on Debian/Ubuntu,
`clang-libclang` on Alpine; set `LIBCLANG_PATH` to the directory containing
the library if it is somewhere non-standard). With `--features vendored`,
libtorrent is built from the pinned
submodule and statically linked; only system libraries (OpenSSL, libc,
libstdc++) remain dynamic. Without it a system libtorrent-rasterbar ≥ 2.1 is
used instead (found via CMake config or pkg-config; force a prefix with
`CTORRENT_LIBTORRENT_PREFIX`) and linked the way that library was built.

An example config lives at [`rsbtd/etc/rsbtd.toml`](rsbtd/etc/rsbtd.toml) and
a hardened systemd unit at [`rsbtd/etc/rsbtd.service`](rsbtd/etc/rsbtd.service)
(it expects the binary at `/usr/local/bin/rsbtd`).

On Windows, a plain `cargo build --features vendored -p rsbtd -p rsbtctl`
works in a VS x64 dev shell with a few environment variables set — see
[windows/README.md](windows/README.md).

## Third-party notices

Because the release binaries statically link libtorrent (BSD-3-Clause),
Boost, the whole Rust crate closure, and (on Windows) OpenSSL — and the
packages ship the built web UI with its npm dependency closure — every
binary artifact carries a consolidated notice bundle,
[`THIRD-PARTY-NOTICES.md`](THIRD-PARTY-NOTICES.md):

- **RPMs**: `%license`, installed under `/usr/share/licenses/rsbtd/`
  (and `…/rsbtctl/`, `…/rsbtd-webui/`) together with `LICENSE`.
- **Container images**: via the RPMs at the same path; the Alpine CI
  image copies it there directly.
- **MSI**: installed next to the binaries in
  `%LOCALAPPDATA%\Programs\rsbtd`.

The file is generated by `scripts/gen_notices.py` from `Cargo.lock` /
`cargo metadata`, `webui/package-lock.json` + `webui/node_modules`, the
vendored submodule, and the Boost/OpenSSL pins; CI (the `notices` job)
fails if it drifts from those inputs. After changing any of them,
regenerate on Linux (with `npm ci` done in `webui/`) and commit the
diff:

```sh
python3 scripts/gen_notices.py
```

## The web UI

A static single-page app, built separately (Node ≥ 24):

```sh
cd webui && npm ci && npm run build     # → webui/dist
```

Point the daemon's `serve_root` at the resulting `dist/`, or host it on any
static file server. Development setup, scripts, and deployment details:
[webui/README.md](webui/README.md).

## Linux RPMs

`packaging/build-rpm.sh` builds the RPMs inside an Oracle Linux 10 builder
container: pinned clang/lld and Rust, fat cross-language LTO across
libtorrent, the C shim, and the Rust code, and the full test suite in
`%check`. Host requirements: `podman` (or `docker` with
`CONTAINER_ENGINE=docker`), `git`, initialized submodules, and a built web UI
(see above, or set `RSBTD_WEBUI_DIST`).

```sh
packaging/build-rpm.sh      # → dist/rpms/*.rpm  (rsbtd, rsbtctl, rsbtd-webui, debuginfo, SRPM)
```

Details — the LTO scheme, version pins, cache knobs:
[packaging/README.md](packaging/README.md).

## Container image

Release images are published at `ghcr.io/namazso/rsbtd`, so you only need
this to modify the image or run unreleased code. `packaging/build-image.sh`
assembles the production image from the RPMs in `dist/rpms/`. Nothing is
compiled at this stage, so you can also feed it the RPMs from a
[release](https://github.com/namazso/rsbtd/releases) instead of building them:

```sh
mkdir -p dist/rpms
cp /path/to/{rsbtd,rsbtctl,rsbtd-webui}-*.rpm dist/rpms/
packaging/build-image.sh                # → localhost/rsbtd:<version>
```

If `dist/rpms/` has no RPMs, the script runs `build-rpm.sh` first. The image
is based on `oraclelinux:10-slim`, runs as the `rsbtd` user, listens on
`:3928` (API + web UI) and `:6881` TCP/UDP (peers), serves the bundled web UI
on `/`, and declares `/var/lib/rsbtd` as a volume.

## Windows MSI

`windows/build.ps1` is the canonical Windows build: the same pinned LLVM/Rust
and cross-language LTO as the RPMs, the full workspace test suite, and a WiX
MSI installer.

```powershell
cd webui; npm ci; npm run build; cd ..
windows\build.ps1 -WebUiDist webui\dist     # → dist\windows\rsbtd-<version>-x64.msi
windows\build.ps1 -WebUiDist webui\dist -Arch arm64   # cross-compiled arm64 MSI
```

Requirements (checked by the script, not installed): Visual Studio 2022 Build
Tools, the pinned LLVM, Rust via rustup, CMake ≥ 3.25, Ninja, NASM, Perl, and
WiX ≥ 6. Details, including the installer's behavior:
[windows/README.md](windows/README.md).

## Repository layout

The daemon is the product; the rest of the workspace is its building blocks:

| Crate / dir | What it is |
|---|---|
| `rsbtd/` | The daemon (on Windows: a tray app, source in `rsbtd/src/windows/`) |
| `rsbtctl/` | Command-line client for the daemon |
| `webui/` | Web UI (React SPA; see [webui/README.md](webui/README.md)) |
| `rbtorrent/` | Async-first Rust bindings for libtorrent |
| `libctorrent/` + `libctorrent-sys/` | C shim over libtorrent and its raw FFI bindings |
| `vendor/libtorrent` | Pinned libtorrent submodule (RC_2_1) |
| `packaging/` | Linux RPM + container build (see [packaging/README.md](packaging/README.md)) |
| `windows/` | Windows build + MSI installer (see [windows/README.md](windows/README.md)) |

## Development notes

- `cargo test --workspace --features vendored` runs the full suite;
  `scripts/gen_settings.py` and `scripts/gen_alerts.py` regenerate checked-in
  sources from the pinned submodule (CI enforces a clean regen).
- The shim compiles at `TORRENT_ABI_VERSION` 2 and 100; layout facts are
  probed at CMake configure time and `static_assert`ed, so a mismatched system
  libtorrent fails at build time, never at runtime.
- CI (`.github/workflows/ci.yml`) runs the test matrix (ABI 2 and 100), the
  C++ shim's standalone tests, docs/lint/regen/notices checks, and all three
  canonical builds; on `v*` tags it attaches the MSI and RPMs to the GitHub
  release.
